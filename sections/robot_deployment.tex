\section{Real Robot Demonstration}

% The experiments above evaluate the typing step in isolation, on hand-authored problems. To show that this step composes into a working system rather than depending on curated PDDL, we deploy the full pipeline on a physical robot, where the typed problem is constructed end-to-end from raw perception rather than provided a priori.

To demonstrate that CAST can also be integrated into a complete robotic system, we deploy the full pipeline on a Stretch mobile manipulator~\cite{stretch}. In this setting, the planning problem is generated at runtime from perception outputs rather than specified manually in advance.

Figure~\ref{fig:robot_example} illustrates the deployment pipeline. The robot's planning domain includes actions such as \texttt{pickup} and \texttt{clean\_blackboard}, whose typed parameters restrict the objects with which they can be instantiated. At runtime, Grounding DINO~\cite{gdino} detects objects in the scene, and SAM 2~\cite{sam} provides their segmentations. These outputs are used to obtain semantic class labels and estimated 3D positions. Although the perception system identifies what objects are present and where they are located, it does not determine which planner-specific functional roles those objects can fulfill. Detected manipulable objects are therefore initially assigned the abstract base type \texttt{graspable}. CAST then assigns goal-relevant objects to appropriate symbolic types before the problem is passed to the planner. In this deployment, the typing gap thus arises directly at the perception--planning interface.

The domain includes actions such as \texttt{pickup} and \texttt{clean\_blackboard}, each with typed preconditions that constrain which objects they can be applied to. At runtime the scene is perceived using Grounding DINO~\cite{gdino} for object detection and SAM 2~\cite{sam} for segmentation, yielding a set of detected objects with semantic class names and estimated 3D positions. The system knows, for example, that a \texttt{cloth} is present, but has no knowledge of the affordances required by the planner. Accordingly, all detected objects are assigned the abstract base type \texttt{graspable} in the generated PDDL problem, and the LLM must assign appropriate types before planning can proceed. This is precisely the typing gap CAST resolves, now arising organically from perception: the vision stack reports \emph{what} is in the scene, but not \emph{what role} each object can play.

The accompanying video demonstrates the example shown in Figure~\ref{fig:robot_example}. With no \texttt{eraser} present, CAST identifies the detected \texttt{cloth} as a functional substitute, assigns it the corresponding symbolic type, and enables the robot to complete the whiteboard-cleaning task. We present this as an integration demonstration rather than a quantitative benchmark.
