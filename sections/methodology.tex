\section{Methodology}

In this section we present three LLM querying strategies for resolving typing gaps at runtime, each representing different trade-offs between token cost, flexibility, and robustness. All three approaches share a common structure: given an untyped or partially typed PDDL problem, an LLM is queried to assign types to available objects, and the resulting typed problem is passed to a symbolic planner. They differ in how the LLM is queried, how feedback is incorporated, and how disagreement is resolved.

\subsection{Consensus Based Typing}
The consensus-based approach exploits the stochastic nature of LLMs: repeated queries over the same prompt may yield distinct type assignments. By querying the LLM $q$ times, we build a distribution of votes over mappings between each object $o$ and candidate types $\tau \in \mathcal{T}$.

Algorithm~\ref{alg:consensus-typing} formalises this approach. The LLM generates $q$ candidate assignments $\hat{\sigma}$, from which a majority-vote assignment $\hat{\tau}$ is derived by selecting the most-voted type per object. The planner is first attempted under $\hat{\tau}$; if a plan is found, we terminate. Otherwise, for each object with type disagreement across queries, we substitute alternative types one object at a time, keeping all others at their majority type, in order of ascending confidence, attempting the planner after each substitution. We return the first plan found, or $\emptyset$ if no substitution yields a solution. This recovery explores only single-object relaxations of the majority assignment; problems that require several objects to be simultaneously re-typed beyond the majority vote --- as arise when a goal demands multiple distinct substitutions --- may therefore be missed, a limitation reflected in the bulk results.

\begin{algorithm}
  \caption{Consensus Semantic Typing}
  \label{alg:consensus-typing}
  \begin{algorithmic}[1]
    \footnotesize
    \Require domain $D$, problem $P=\langle O,I,G\rangle$, LLM, planner, number of queries $q$, prompt $\rho_T$
    
    \State $\mathcal{S} \gets [\,]$
    
    \For{$i = 1$ to $q$} 
      \State $\mathcal{S}.\mathrm{append}(LLM(D, P, \rho_T))$ \Comment{collect candidate $\hat{\sigma}$}
    \EndFor
    
    \State $\hat{\tau} \gets \mathrm{MajorityVote}(\mathcal{S})$ \Comment{$\mathrm{argmax}$ per object}
    \State $A_o \gets [t \mid \mathrm{votes}(o,t) > 0]$ sorted by $\downarrow$ votes
    \State $\mathcal{U} \gets [(o,\, A_o) \mid o \in O,\; |A_o| > 1]$ sorted by $\uparrow$ confidence$(o)$
    
    \For{each $(o, A_o) \in \mathcal{U}$} 
      \For{each $t \in A_o$}
        \State $\tau' \gets \hat{\tau}$ with $o \mapsto t$ 
        \State $\mathcal{P} \gets Planner(D, P|_{\tau'})$
        \If{$\mathcal{P} \neq \emptyset$} 
          \State \Return $\mathcal{P}$
        \EndIf 
      \EndFor 
    \EndFor
    
    \State \Return $\emptyset$
  \end{algorithmic}
\end{algorithm}

\subsection{Iterative Typing}
While consensus-based typing always issues exactly $q$ queries, iterative typing (Algorithm~\ref{alg:iterative}) can succeed in as few as one. Under this approach, the LLM is queried once for a type assignment $\hat{\sigma}$ and the planner is invoked. Upon failure, the LLM is re-queried with feedback and given the opportunity to revise its proposal. This feedback loop is the key distinction from consensus: rather than aggregating independent samples, the LLM is guided toward a valid assignment through re-querying. The procedure repeats for at most $T$ iterations, returning the first plan found or $\emptyset$ if none is found within the budget.

The content of the feedback passed to the LLM is flexible. In the simplest case, a boolean signal indicating only that the planner failed may be used. In our implementation, we attempt to provide richer feedback including the previous queries object-to-type assignments along with the fact the planner has failure. The LLM is instructed to reconsider $\hat{\sigma}$.

\begin{algorithm}
  \caption{Iterative Typing}
  \label{alg:iterative}
  \begin{algorithmic}[1]
    \footnotesize
    \Require domain $D$, problem $P=\langle O,I,G\rangle$, LLM, planner, max iterations $T$, prompt $\rho_T$
    
    \State $f \gets \texttt{null}$ \Comment{no feedback on first call}
    
    \For{$t = 1$ to $T$} 
      \State $\hat{\sigma} \gets LLM(D, P, \rho_T, f)$
      \State $\mathcal{P} \gets Planner(D, P|_{\hat{\sigma}})$
      \If{$\mathcal{P} \neq \emptyset$} 
        \State \Return $\mathcal{P}$
      \EndIf 
      \If{$t < T$} 
        \State $f \gets \mathrm{PlannerFeedback}(\hat{\sigma},\, t,\, T)$ 
      \EndIf 
    \EndFor
    
    \State \Return $\emptyset$
  \end{algorithmic}
\end{algorithm}

\subsection{Judge Typing}
Like iterative typing, judge-based typing (Algorithm~\ref{alg:judge}) can succeed in as few as one query. Rather than invoking the planner directly on the LLM's proposed assignment $\hat{\sigma}$, a judge LLM call --- which may use the same model with a different prompt $\rho_J$ --- first evaluates the assignment semantically. If approved, the planner is invoked; otherwise the judge's feedback is passed back to the LLM for refinement. This distinguishes it from iterative typing, where feedback is driven by planner failure: here, semantically poor assignments are filtered before planning is attempted at all.

The judge is prompted to reason at a high level about the proposed $\hat{\sigma}$, evaluating whether goal-relevant objects are correctly typed and whether the assignment is likely to yield a solvable problem. The procedure runs for at most $T$ iterations; if no assignment is approved within budget, the planner is attempted on the final proposal as a fallback.


\begin{algorithm}
  \caption{LLM-Judge Typing}
  \label{alg:judge}
  \begin{algorithmic}[1]
    \footnotesize
    \Require domain $D$, problem $P=\langle O,I,G\rangle$, LLM, Judge, planner, max iterations $T$, prompts $\rho_T,\rho_J$
    
    \State $f \gets \texttt{null}$ \Comment{no feedback on first call}
    
    \For{$t = 1$ to $T$} 
      \State $\hat{\sigma} \gets LLM(D, P, \rho_T, f)$
      \State $j_t \gets Judge(D, P, \hat{\sigma}, \rho_J)$
      \If{$j_t.\mathrm{approved}$} 
        \State \textbf{break} 
      \EndIf 
      \State $f \gets j_t.\mathrm{feedback}$ 
    \EndFor
    
    \State \Return $Planner(D, P|_{\hat{\sigma}})$
  \end{algorithmic}
\end{algorithm}
